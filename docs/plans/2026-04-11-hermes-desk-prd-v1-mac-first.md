# Hermes Desk PRD v1（Mac-first）

> **文档定位**：Phase 0 / Phase 1 产品需求文档  
> **目标**：先做出一个让程序员自己愿意长期挂在 MenuBar 的 Agent 监督控制面  
> **范围**：只做 Mac 原生客户端，只接 Hermes 单 Adapter；暂不做 iPhone、P2P、链上、多 Agent 生态

---

## 1. 问题定义

### 1.1 背景
当前 Hermes / OpenClaw / Claude Code 这类 Agent 已经具备多步执行、工具调用、后台运行和人工确认能力，但其主交互入口仍以 CLI / 聊天窗口为主。对于重度使用者，最大问题不是“Agent 不够强”，而是：

1. 不盯终端就不知道它在干嘛
2. 到了确认点没有一个高效、可信、可回看的处理界面
3. 失败后只能从混乱日志中找原因
4. 任务结束后缺少清晰结果卡片与可复用产物

### 1.2 核心问题
Agent 的本质是 **Task-based**，而不是 **Chat-based**。  
因此，用户需要的不是“又一个聊天壳”，而是：

> **一个能监督任务、处理确认、快速止损、回看结果的控制面。**

### 1.3 本期产品定义
Hermes Desk v1 不是移动端遥控器，而是：

> **Mac 上的 Agent 监督控制面（Supervisor Control Layer）**

它要先解决以下问题：
- 我不盯 Hermes CLI 时，是否仍能知道任务状态
- Hermes 请求确认时，我能否快速理解并决策
- Hermes 失败时，我能否快速止损和恢复
- 任务结束后，我能否获得结构化结果，而不是长消息流

---

## 2. 已知事实 / 推断 / 决策

### 2.1 已知事实
- Hermes 现有代码库已经提供本机 API Server：
  - `GET /health`
  - `POST /v1/chat/completions`
  - `POST /v1/runs`
  - `GET /v1/runs/{run_id}/events`（SSE）
- Hermes 已有 macOS launchd 管理逻辑
- Hermes 已存在确认流、后台任务、会话持久化等基础能力
- 用户当前明确要求：
  - 先 Mac 原生开发
  - 先只接 Hermes
  - 第一版不追求“好看”，优先“程序员觉得好用”
  - 先完成 Phase 0 和 Phase 1

### 2.2 推断
- MVP 最大价值不在“发起聊天”，而在“监督 + 确认 + 恢复 + 回看”
- 第一阶段最适合的交互形态不是大而全桌面 App，而是 **MenuBar 常驻 + 少量独立工作窗口**
- 若过早进入 iPhone / 中继 / Web3 / P2P，会显著拖慢核心价值验证

### 2.3 决策
本 PRD 的明确决策如下：
1. **Mac-first**
2. **Hermes-only**
3. **Native-first（SwiftUI + 少量 AppKit 桥接）**
4. **Task-first，不以聊天列表为首页**
5. **先做监督闭环，再做远程闭环**

---

## 3. 目标用户

### 3.1 本期目标用户（Must-have）
- 长时间使用 Hermes 的程序员 / 自动化工作流用户
- 需要在本机后台跑 Agent，但不想一直盯终端
- 愿意用 MenuBar 工具和桌面控制面板管理任务的人

### 3.2 非本期目标用户（Not now）
- 完全不懂 Agent 的普通用户
- 团队协作场景下的多角色用户
- 仅偶发性使用 AI 聊天的人

### 3.3 核心 JTBD
当我在 Mac 上让 Hermes 跑任务时，
- 我想快速知道它**现在在做什么**
- 我想在需要时**快速确认/拒绝**
- 我想在失败时**迅速恢复或终止**
- 我想在结束后**直接看到可复用结果**
这样我就不需要盯着 CLI，也不会因为信息过载而失控。

## 4. 产品目标与非目标

## 4.1 Product Goals
### G1. 任务状态可见
用户打开 MenuBar 后，3 秒内能回答：
- Hermes 是否在线
- 当前是否有运行中任务
- 当前是否有待确认任务
- 是否有失败待恢复任务

### G2. 确认流高效可信
当 Hermes 请求确认时，用户能在 Hermes Desk 中看到：
- 它要做什么
- 为什么危险
- 命令 / 路径 / patch 的关键证据
- 允许 / 拒绝 / 更细粒度授权选项

### G3. 失败后可恢复
当 Hermes 出错或中断时，Hermes Desk 能提供明确恢复动作：
- 重试
- 恢复
- 终止
- 打开终端 / 工作区 / 日志

### G4. 结果可回看可复用
任务结束后，用户能看到结构化结果卡片，而不是只能翻历史消息。

## 4.2 Non-goals
本期明确不做：
1. iPhone / iPad 客户端
2. 远程中继 / P2P / 链上发现
3. 多 Agent Marketplace
4. 复杂美术视觉体系
5. 团队协作、共享审批、RBAC
6. 通用聊天 App 首页

---

## 5. 关键体验原则

1. **任务优先，不是聊天优先**
2. **待处理事项优先，不是信息流优先**
3. **默认只展示决策需要的信息**
4. **失败是主路径，不是边缘情况**
5. **动作必须与底层真实能力一致**
6. **对程序员友好：文本优先、键盘优先、可复制优先**

---

## 6. 核心使用流程

## 6.1 Flow A：查看整体状态
1. 用户点击 MenuBar 图标
2. 看到 Hermes 连接状态与任务总览
3. 第一屏优先看到：待确认、失败待恢复、运行中、最近完成
4. 用户点入具体任务详情

**成功标准**：3 秒内定位当前最需要处理的事

## 6.2 Flow B：处理确认
1. Hermes 发出确认请求
2. Hermes Desk 在 MenuBar 和详情页中高亮该任务
3. 用户点开确认卡片
4. 查看简明说明 + 命令 / patch / 路径证据
5. 选择：允许一次 / 本任务内允许 / 拒绝（Phase 1 再考虑“总是允许”）
6. 任务继续执行，卡片转为已决议状态

**成功标准**：无需回 CLI 即可完成确认；用户对风险有感知

## 6.3 Flow C：失败恢复
1. Hermes 任务失败
2. Hermes Desk 将任务列入“待恢复”优先区
3. 用户打开详情页，看到失败分类、失败位置、上下文摘要
4. 用户执行：重试 / 恢复 / 打开终端 / 取消

**成功标准**：用户不需要先读长日志才能找到“下一步”

## 6.4 Flow D：回看结果
1. 任务完成
2. 任务进入 Recent 区
3. 用户点开任务详情
4. 看到 result card：摘要、关键输出、相关路径/文件、后续建议

**成功标准**：用户能把任务结果当成产物，而不是聊天尾巴

## 7. MVP 页面定义

## 7.1 页面 P1：MenuBar Popover（最高优先级）
### 目标
作为统一入口，承担状态总览与待处理事项收件箱。

### 内容结构
#### A. 顶部状态区
- Hermes 状态：在线 / 启动中 / 失联 / 配置错误
- 任务统计：运行中 N、待确认 N、失败 N
- 快捷动作：新建任务、查看全部、设置

#### B. Inbox 区（优先级最高）
- 待确认
- 失败待恢复
- 需要补充信息

#### C. Running 区
每个任务显示：
- 标题
- 当前阶段（如：读取代码 / 跑测试 / 等待确认）
- 最新关键事件
- 耗时

#### D. Recent 区
- 最近完成 / 最近失败
- 打开详情
- 复制结果
- 重新运行（Phase 1）

### 验收标准
- 默认打开后不出现聊天欢迎页
- 默认优先显示“待处理事项”
- 点击任一任务能进入详情页

## 7.2 页面 P2：Task Detail Window
### 目标
承担任务的主要工作界面。

### 内容结构
#### Header
- 标题
- 状态
- 创建时间 / 更新时间 / 耗时
- 快捷动作：重试 / 恢复 / 取消 / 复制结果 / 在终端打开

#### 主时间线 Timeline
事件类型：
- 用户目标
- Agent 计划
- step
- confirm
- error
- result

#### 当前阶段主面板
按状态切换：
- Running：显示当前步骤 + 最新输出
- Waiting User：显示确认卡片
- Failed：显示失败详情 + 恢复动作
- Succeeded：显示结果卡片

#### Debug / Artifact 区
- 命令预览
- 路径
- 文件变更摘要
- 日志片段
- 可复制 ID（session/task/run/process）

### 验收标准
- 用户能明确看到任务卡在哪里
- 每种状态下都有可执行动作
- 默认不把 log 全量展开

## 7.3 页面 P3：Confirmation Card
### 目标
把“确认流”做成稳定、可信、可快速决策的 UI 组件。

### 必须信息
- 它要做什么
- 为什么危险
- 命令 / patch / 路径预览
- 授权范围
- 决策按钮

### 按钮定义
#### Phase 0
- 允许一次
- 拒绝
- 查看完整上下文
- 在终端打开

#### Phase 1
- 本任务内允许
- 编辑后执行
- 复制命令 / patch

### 验收标准
- 可完全键盘操作
- 决策后卡片进入“已决议”状态
- 用户可回看确认历史

## 7.4 页面 P4：Settings / Diagnostics
### 目标
当 Hermes 连接、配置或状态有问题时，30 秒内能定位。

### 必须内容
- 当前 Adapter：Hermes
- Hermes 地址 / 端口 / 鉴权状态
- Launchd / 服务状态
- 当前 profile / workspace（只读优先）
- 日志入口
- 重连 / 健康检查 / 清理卡死任务

### 验收标准
- 至少能定位“为什么连不上 Hermes”
- 允许用户一键执行健康检查

## 8. 功能需求

## 8.1 Phase 0（必须做）
| 模块 | 必须能力 |
|---|---|
| 连接 | 健康检查、在线/离线状态、基础重连 |
| 任务 | 运行中/待确认/失败/完成四类总览 |
| 详情 | Timeline、当前阶段主面板、结果卡片 |
| 确认 | allow once / deny |
| 失败 | 错误展示、重试、打开终端/日志 |
| 结果 | summary + 关键产物 |
| 基础体验 | 流式输出、复制、键盘快捷操作 |

## 8.2 Phase 1（增强）
| 模块 | 增强能力 |
|---|---|
| 连接 | 更稳健的重连与诊断页 |
| 任务 | 最近任务历史、快速重跑 |
| 确认 | task-level allow、编辑后执行 |
| 状态 | 更细的 step / event 呈现 |
| Debug | 打开工作区、复制命令、复制 diff |
| 体验 | 全局快捷键呼出、系统通知优化 |

---

## 9. 非功能需求

### 9.1 性能
- MenuBar 打开时间尽量 < 300ms
- Hermes 已在线时，状态刷新 < 1s
- 任务列表首屏应优先展示摘要，而不是等待全量详情

### 9.2 可恢复性
- Hermes 暂时断开时，UI 不崩溃，状态明确为“失联/重连中”
- 对每个失败任务提供恢复或终止路径

### 9.3 可解释性
- 默认展示与决策相关的信息，不默认展示全量日志
- 每个异常状态必须有人话说明与建议动作

### 9.4 可观测性
- 客户端自身有 OSLog
- 能复制诊断信息
- 记录关键用户动作（打开任务、确认、拒绝、重试、恢复）

---

## 10. 成功指标（先用于自用验证）

| 指标 | 定义 | 目标 |
|---|---|---|
| 状态可见性成功率 | 打开后 3 秒内知道最重要待办 | >80% 自评达成 |
| 确认回 CLI 率 | 处理确认时是否还必须回 CLI | 越低越好 |
| 失败恢复完成率 | 失败后能从 UI 找到下一步并执行 | >70% 自评达成 |
| 结果回看率 | 任务完成后是否通过 result card 回看 | 有显著发生 |
| MenuBar 留存感 | 用户是否愿意长期挂在 MenuBar | 3~7 天持续使用 |

---

## 11. 依赖与风险

### 11.1 依赖
- Hermes API Server 可稳定使用
- Hermes gateway / launchd 生命周期可被可靠检测
- Hermes 确认流与任务事件可被接到 Hermes Desk 的 UI 模型中

### 11.2 风险
| 风险 | 说明 | 缓解 |
|---|---|---|
| Hermes 生命周期不稳定 | 服务状态与 UI 状态不同步 | 优先把诊断页做实 |
| 事件粒度不足 | UI 难以做 Timeline / step 展示 | Phase 0 先最小集成，Phase 1 再丰富 events |
| UI 承诺过多 | 底层不支持 pause/resume 等动作 | 以 capability 驱动按钮显示 |
| 过度聊天化 | 详情页被做成气泡消息流 | 强制以任务页结构为主 |

---

## 12. 上线判定（Phase 0 → Phase 1）
满足以下条件，才能认为 Phase 0 成立并进入 Phase 1：

1. 用户愿意持续把它挂在 MenuBar
2. 至少能完整处理真实 Hermes 任务的查看 / 确认 / 失败恢复 / 结果回看闭环
3. 用户不需要频繁切回 CLI 才能知道“现在该做什么”
4. 至少 3~7 天自用后，问题更多是“体验增强项”，而不是“核心结构不成立”
