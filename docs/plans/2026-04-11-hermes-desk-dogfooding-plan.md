# Hermes Desk 3~7 天自用验证方案（Mac-first）

> **目标**：验证 Hermes Desk Phase 0 / 1 是否真的比直接盯 Hermes CLI 更好用  
> **适用范围**：只针对 Mac 原生 Hermes Desk + Hermes 单 Adapter

---

## 1. 验证目标

本轮 dogfooding 不验证商业模式，不验证 iPhone，不验证“普通人是否会用”。

只验证 4 件事：
1. 我是否愿意长期把它挂在 MenuBar
2. 它是否真的降低了我盯 CLI 的频率
3. 它是否让确认 / 失败恢复变得更快
4. 它是否能把任务结果沉淀成有价值的结果卡片

---

## 2. 验证原则

### 已知事实
- 第一版不追求好看，追求“程序员觉得好用”
- 先只接 Hermes
- 先做完 Phase 0 / 1 再决定后续方向

### 建议
dogfooding 时严格避免两个误区：
1. 因为是自己写的，所以自动容忍糟糕交互
2. 因为功能还不全，所以不给产品真正任务

必须用它做真实 Hermes 任务，而不是 demo 任务。

---

## 3. 观察场景

每天尽量覆盖以下场景：

| 场景 | 目的 |
|---|---|
| 启动后查看状态 | 看 MenuBar 是否真是收件箱 |
| 发起一个真实任务 | 看任务模型是否清晰 |
| 遇到确认请求 | 看确认卡片是否足够快、准、稳 |
| 遇到失败 | 看恢复是否比 CLI 更顺手 |
| 任务结束后回看 | 看 result card 是否有价值 |
| Hermes 掉线/异常 | 看 diagnostics 是否够用 |

## 5. 核心指标

## 5.1 必看指标
| 指标 | 定义 | 记录方式 |
|---|---|---|
| 状态识别速度 | 打开后多久知道最重要待办 | 主观计时/自评 |
| CLI 回切率 | 多少次必须切回 CLI 才能继续 | 每次记录 |
| 确认完成率 | 确认是否能在 Hub 内完成 | 每次记录 |
| 失败恢复完成率 | 失败后是否能用 Hub 找到下一步 | 每次记录 |
| 结果回看率 | 完成后是否主动看 result card | 每日记录 |
| MenuBar 留存感 | 是否愿意常驻使用 | 每日打分 |

## 5.2 关键阈值（建议）
| 指标 | 目标 |
|---|---|
| 确认回 CLI 率 | 越低越好，最好显著下降 |
| 失败恢复完成率 | > 70% |
| 愿意长期挂 MenuBar | 平均分 ≥ 4/5 |
| 核心任务监督成功率 | > 60% |

## 6. 重点观察问题

每天都重点回答下面几个问题：

### Q1. MenuBar 真的是“任务收件箱”吗？
还是只是一个启动器？

### Q2. 确认卡片真的足够快吗？
是否仍然因为看不懂命令/上下文而回到 CLI？

### Q3. 失败恢复是否成立？
失败后用户看到的是“下一步动作”，还是“更多错误信息”？

### Q4. Task Detail 是否回答了 4 个问题？
1. 它现在在干嘛？
2. 卡住了吗？
3. 要不要我操作？
4. 失败后我该点哪里？

### Q5. Result Card 是否真的有价值？
是否比翻聊天历史更高效？

---

## 7. Dogfooding 结束后的决策标准

### 如果以下大多数成立，则 Phase 0 / 1 方向正确
- 愿意长期挂 MenuBar
- 状态识别明显快于 CLI
- 确认大多能在 Hub 内完成
- 失败后知道下一步去哪点
- 结果卡片被反复使用

### 如果以下大多数成立，则需要重构而不是继续堆功能
- 经常回 CLI 才能理解任务
- 任务详情页仍像聊天记录而不是任务页
- 确认卡片只是在“包装一个弹窗”
- 失败后仍只能读日志
- MenuBar 入口没有形成使用习惯

---

## 8. 阶段结束输出

dogfooding 结束后，必须产出一页复盘，结构固定：

1. 最有价值的 3 个场景
2. 最失败的 3 个场景
3. 最应该保留的 3 个设计
4. 最应该重做的 3 个设计
5. 是否进入 iPhone 阶段
6. 是否需要先补协议/状态机/恢复模型

---

## 9. 最终判断问题

这轮验证结束后，只回答一个问题：

> **如果它今天已经在我电脑上，我会不会自然而然地一直开着它，而不是继续只看 Hermes CLI？**

如果答案是“会”，Phase 0 / 1 就成立。  
如果答案是“不会”，就别急着加 iPhone，先把 Mac 端打磨到成立。
